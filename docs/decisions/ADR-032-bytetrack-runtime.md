# ADR-032. ByteTrack, идентичность и сброс сцены

Статус: принято (Milestone 5); уточняет ADR-003.

## Библиотека и параметры

ByteTrack вынесен разработчиком из `supervision`: в `supervision 0.31.1` прежнего класса уже нет. Используем `trackers 2.6.1` (Apache-2.0) и `supervision 0.31.1` (MIT), версии закреплены в `uv.lock`; проверены PyPI-метаданные и код установленной реализации. Источники: [trackers](https://pypi.org/project/trackers/2.6.1/), [supervision](https://pypi.org/project/supervision/0.31.1/), [реализация](https://github.com/roboflow/trackers). Готовый алгоритм остаётся за `PersonTracker`, собственной реализации association/Kalman нет. Дополнительные модели, appearance features и re-ID не используются.

`minimum_iou_threshold = TRACK_MATCH_IOU` — настоящий IoU, без преобразования `1-IoU` и без confidence fusion. `track_activation_threshold` и граница high/low равны `TRACK_ACTIVATION_CONFIDENCE`: confidence ровно 0.25 допускает нового кандидата; более слабая детекция может только поддержать существующий трек, если детектор её пропустил. В Milestone 4 детектор уже фильтрует по порогу камеры, поэтому при default 0.25 слабые боксы до трекера не доходят. Отдельный скрытый низкий порог детектора не добавляем.

`frame_rate=30`, `lost_track_buffer=PERSON_TRACK_MAX_AGE`, `timestamp=None`: один update соответствует одному **обработанному** кадру, без привязки к FPS захвата или wall clock. Domain registry удаляет трек на N-м последовательном пропуске (`>= N`) и сразу удаляет соответствующий внутренний tracklet, не допуская позднего воскрешения ID. Проверены границы N=1 и N=25. Изображение в ByteTrack не передаётся.

## Идентичность и данные

Реестр tracker'ов принадлежит одиночному inference executor, ключ `(camera_id, run_id)`. Он очищается при stop/delete/restart/ERROR и штатном shutdown, включая отсутствие новых кадров. Изменение FPS/confidence не сбрасывает ID. Ошибка трекера логируется, камера получает существующую inference_error/DEGRADED; частично изменённая сцена сбрасывается. Другие камеры продолжают обрабатываться.

Библиотечные ID не публикуются: adapter выдаёт возрастающий положительный `track_id`. Новый кандидат получает ID только на следующем совпадении (особенность выбранной реализации); до этого видна обычная детекция без ID. `first_seen`, `age` и `hits` начинаются с **подтверждения** кандидата. `age` растёт на каждом update, `hits` — только при совпадении; `last_seen` и bbox сохраняют последнее наблюдение, а не предсказание. Длительности будущих правил должны использовать source timestamps, не разность wall clock.

`PersonTrack` — immutable dataclass; состояния сейчас `NORMAL`/`LOST`. Center — геометрический центр, anchor — низ-центр для будущих зон. `LOST` хранится для восстановления идентичности, но его старый bbox **не рисуется поверх текущего кадра** и не увеличивает счётчик людей. История всех когда-либо выданных ID не копится: только активные/LOST записи и один счётчик.

## Разрыв сцены

При цикле файла/mock, переподключении источника или смене разрешения tracker сбрасывается, но публичный счётчик ID внутри run не обнуляется. Новый run может начать с ID 1. Идентичность всегда включает камеру и run, межкамерного распознавания нет.

Одного `Frame.discontinuity` недостаточно: этот кадр может быть вытеснен из latest-frame буфера. Поэтому capture session повышает `source_epoch` на разрыве и первом кадре после open/reconnect, копируя только dataclass, не numpy-изображение. Каждый последующий кадр несёт этот epoch; обработчик обнаружит смену даже после пропуска помеченного кадра. Epoch внутренний, не добавляется в REST/Redis. Preview по-прежнему атомарен по frame/run.

Хранение track sessions, сегментов и аналитики не добавлено: это дальнейшие этапы по ADR-019. Потеря runtime-треков при аварии ожидаема.
